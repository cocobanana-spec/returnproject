## 1. 공통 설계 원칙

- **서버가 규칙을 지킨다.** 무료·유료 구분, 만료, 발송 한도는 전부 RPC·엣지 함수에서 검사한다. 앱 화면의 검사는 안내용이다. 1단계의 RLS·RPC 원칙(docs/03)을 그대로 잇는다.
- **소유 축은 장부다.** 청첩장도 문자 발송 기록도 `ledger_id` 를 가진다. 부부가 같이 만든다(docs/03 §10 에서 이미 정한 것).
- **외부 사람의 데이터는 최소로 만진다.** 청첩장에 적히는 상주·계좌, 문자 수신자 번호는 발행자가 책임지는 정보다. 우리는 보여 주거나 보내는 데 필요한 만큼만 저장하고, 끝나면 지운다.
- **네이티브 재빌드는 묶어서 한다.** 사진 선택(②), 연락처(③), 웹뷰(②)가 새 네이티브 모듈이다. 한 번의 빌드에 같이 넣어 TestFlight 왕복을 줄인다.

## 2. 기능 ① 웹 주소

### 2.1 현재 문제
`https://cocobanana-spec.github.io/returnproject/app/` — 사용자 이름·저장소 이름·경로가 다 드러난다. 카카오톡으로 공유하면 주소만으로는 무엇인지 알 수 없다. 청첩장 링크를 이 밑에 두면 더 길어진다.

### 2.2 이름 — `ppurin.com` (2026-10-03 결정)
번들 ID(`com.cocobanana.ppurin`), 딥링크 스킴(`ppurin://`), 스토어 SKU(`ppurin-001`)가 전부 `ppurin` 이다. 주소도 같게 둔다.
**`.kr` 이 아니라 `.com` 으로 정했다.** 미국·일본 확장을 보기 때문이다(사용자 결정). whois·DNS·RDAP 세 경로에서 모두 미등록으로 확인했다.

| 후보 | 상태 (2026-10-03 whois) | 비고 |
|---|---|---|
| **`ppurin.com`** | 미등록 (Verisign whois·RDAP 404·DNS 없음) | **확정.** 해외 확장에 맞다 |
| `ppurin.kr` | 미등록 (KRNIC 확인) | 방어용으로 같이 사면 좋다. 선택 |
| `ppurin.co.kr` | 미등록 | 길다. 안 산다 |
| `ppurin.app` | 판단 불가 (구글 레지스트리 조회 형식) | 등록 대행사에서 확인. HTTPS 강제라 랜딩용으로는 좋다 |

`뿌린대로.kr` 같은 한글 도메인은 카카오톡·문자에서 `xn--` 로 깨져 보일 수 있어 뺀다.

### 2.3 주소 구조

| 주소 | 무엇 | 지금 |
|---|---|---|
| `https://ppurin.com/` | 랜딩 | `/returnproject/` |
| `https://app.ppurin.com/` | 웹 앱 | `/returnproject/app/` |
| `https://ppurin.com/i/{코드}` | 청첩장·부고장 공개 페이지 (②) | 없음 |
| `https://ppurin.com/privacy` | 처리방침 | `/returnproject/privacy.html` |

웹 앱을 `app.` 하위 도메인으로 떼는 이유 — 랜딩·청첩장 페이지는 정적이고 빨라야 하며, 웹 앱은 단일 페이지 앱이라 404 폴백·캐시 규칙이 다르다. 한 도메인에 섞으면 지금처럼 "루트 404.html 이 앱이어야 한다" 같은 꼬임이 생긴다. 청첩장 링크는 가장 많이 공유되므로 가장 짧은 루트 밑(`/i/`)에 둔다.

### 2.4 호스팅 — Cloudflare Pages 로 옮긴다
GitHub Pages 를 그대로 두고 도메인만 붙일 수도 있다. 그런데 **②의 공개 페이지는 카카오톡 미리보기(og:image·제목)를 청첩장마다 다르게 내야 하고, 카카오톡은 자바스크립트를 실행하지 않는다.** 정적 호스팅으로는 불가능하다. Cloudflare Pages 는 무료 구간에서 서버 함수(Pages Functions)를 주므로 `/i/{코드}` 요청에 서버가 HTML 을 만들어 줄 수 있다. 그 밖에도 한국 쪽 엣지가 가깝고, 단일 페이지 앱 폴백(`_redirects`)이 정식 기능이며, DNS·HTTPS 가 같은 곳에서 끝난다.

### 2.5 이전 절차 — 무중단
1. 사장님 — **Cloudflare 에서 바로 산다.** Cloudflare Registrar 는 `.com` 을 원가(연 약 11달러)에 팔고, 어차피 호스팅을 Cloudflare 에 두므로 네임서버를 옮길 일이 없다. 가입 → Domain Registration → `ppurin.com` 검색 → 구매. 10분.
2. 나 — Cloudflare Pages 프로젝트 2개(랜딩+공개 페이지, 웹 앱)를 만들고 `wrangler` 배포 스크립트로 교체한다. `experiments.baseUrl` 을 뗀다(루트 서빙).
3. 새 주소에서 전부 확인한 뒤 **Supabase Redirect URLs 에 새 주소 3종을 더한다. 옛 것은 아직 지우지 않는다.** Site URL 도 바꾼다.
4. 옛 github.io 주소는 새 주소로 보내는 안내 페이지로 바꾼다. 최소 6개월 유지한다.
5. App Store Connect 의 **개인정보 처리방침 URL·지원 URL 을 새 주소로 바꾼다.** 심사 통과 뒤라 안전하다. 옛 주소도 살아 있으므로 바꾸는 사이에 끊기지 않는다.
6. 2주 뒤 옛 Redirect URLs 를 지운다.

Google·Apple 로그인 설정은 손대지 않는다. 둘 다 복귀 주소가 Supabase 의 것이지 우리 도메인이 아니다.

### 2.6 나중에 — 유니버설 링크
도메인이 우리 것이 되면 `ppurin.com/.well-known/apple-app-site-association` 을 둘 수 있다. 그러면 청첩장 링크를 받은 사람이 앱을 깔아 두었을 때 앱이 바로 열린다. 앱 재빌드와 Associated Domains 설정이 필요하므로 ② 3차에 넣는다.

## 3. 기능 ② 청첩장 · 부고장

### 3.1 범위
- **종류** — 청첩장(결혼식), 부고장(장례). 돌잔치 초대장은 같은 엔진으로 나중에 켠다.
- **대상** — 장부의 **내 행사**(`events.is_mine = true`)에 붙는다. 행사 하나에 청첩장 하나.
- **흐름** — 만들기(단계별 입력) → 미리보기 → 발행(링크 생김) → 공유(복사·공유 시트·카카오톡) → N개월 뒤 만료(연장 가능) → 내리기.
- **부고장은 10분 안에 끝나야 한다.** 상을 당한 사람이 쓰는 화면이다. 필수 칸을 고인·상주·빈소·발인·장지·계좌로 줄이고 사진은 선택, 템플릿은 하나로 시작한다.

### 3.2 데이터 모델 (마이그레이션 0009)

```
invitations
  id, ledger_id, event_id (unique), kind ('wedding'|'funeral'),
  template_id text, slug text unique,          -- 10자 base62 무작위. 추측 불가
  content jsonb,                                -- 종류별 고정 스키마. 앱이 zod 로 검증
  status ('draft'|'published'|'unpublished'|'expired'),
  published_at, expires_at, plan ('free'|'premium'),
  view_count int default 0, created_by, created_at, updated_at
entitlements  (프리미엄 기반, §5)
```

- `content` 안에 들어가는 것 — 청첩장은 신랑·신부 이름과 양가 부모, 일시, 예식장·주소, 인사말, 커버 사진·갤러리(스토리지 경로), 축의금 계좌(측별 여러 개). 부고장은 고인, 상주 목록(관계·이름), 빈소, 발인 일시, 장지, 조의금 계좌, 연락처.
- 계좌는 docs/03 §10 의 `bank_accounts` 테이블 대신 `content` 에 둔다. 조회가 청첩장 단위로만 일어나므로 테이블을 나눌 이유가 없다.
- `rsvps` 는 3차에 만든다(§3.6).
- **공개 읽기** — 테이블 자체는 장부 구성원만 읽는다. 외부인은 `public_invitation(slug)` SECURITY DEFINER RPC 로만 읽고, 이 RPC 는 `status = 'published' and expires_at > now()` 일 때만 돌려주며 조회수를 올린다. 사진은 `invitations` 스토리지 버킷에 공개 읽기로 두되 경로에 slug 를 넣어 추측을 막는다.
- **만료** — 하루 한 번 도는 엣지 함수가 `expires_at` 지난 것을 `expired` 로 바꾸고, 30일 더 지나면 사진을 지운다. 글은 남겨 발행자가 다시 발행할 수 있게 한다.

### 3.3 템플릿은 HTML 한 벌로 만든다
템플릿을 앱(React Native)과 공개 페이지(웹)에 따로 만들면 종류마다 두 번 그리고 두 번 고친다. **템플릿을 "내용 → HTML" 함수로 한 번만 만들고**, 공개 페이지는 Cloudflare 함수가 그 HTML 을 내보내며, 앱의 미리보기는 같은 HTML 을 웹뷰로 보여 준다. 웹 앱에서는 iframe 이다.

- 템플릿 = 배치 종류 + 색·글꼴 토큰. **입력 칸은 종류별로 고정**이라 템플릿을 바꿔도 적은 내용이 사라지지 않는다.
- 시작 수량 — 청첩장 3종(단정한 흰색, 사진 중심, 한지 느낌), 부고장 2종(검정 바탕, 흰 바탕).
- 지도는 SDK 를 넣지 않는다. 주소로 카카오맵·네이버지도·티맵 링크를 만들어 "길찾기" 버튼으로 둔다. 지도 SDK 는 키 발급·용량·심사 항목이 늘어난다.
- 공개 페이지는 앱 번들을 싣지 않는다. 지금 웹 앱 번들이 3.5MB 인데 하객은 데이터로 한 번 열어 본다. 서버가 완성된 HTML 을 주면 첫 화면이 바로 뜨고 카카오톡 미리보기도 맞는다.

### 3.4 앱 쪽 (새 네이티브 모듈 2개 → 재빌드)
- 사진 — `expo-image-picker`. iOS 14 이상의 시스템 선택기는 **권한 창 없이** 고른 사진만 넘겨준다. 처리방침과 App Privacy 에 "사진(선택한 것만)"을 더한다.
- 미리보기 — `react-native-webview`.
- 공유 — RN 내장 `Share` 로 공유 시트를 띄운다. 카카오톡은 시트에서 고르면 되고 미리보기는 OG 태그로 잡힌다. 카카오 SDK 는 넣지 않는다(1단계에서 카카오 로그인을 뺀 결정과 같은 이유).

### 3.5 무료와 유료 (나중에 켠다. 지금은 기준만 정한다)

| | 무료 | 프리미엄 |
|---|---|---|
| 동시 발행 | 1건 | 제한 없음 |
| 유지 기간 | 3개월 | 12개월, 연장 가능 |
| 템플릿 | 종류별 1개 | 전부 |
| 하단 표기 "뿌린대로거두리라로 만듦" | 있음 | 없음 |
| 조회수·RSVP | 없음 | 있음 |

유료 모델은 **발행권 1회 구매**(소모성 인앱 결제, 예 9,900원)를 추천한다. 결혼은 일생에 한 번이고 부고는 급한 일이라 구독이 어울리지 않는다. 결정은 §6.

### 3.6 단계
- **2A (3주)** — 0009 마이그레이션·RPC·스토리지, 청첩장 템플릿 1 + 부고장 템플릿 1, 단계별 입력 화면, 발행·공유·만료, Cloudflare 공개 페이지(OG 포함). 내부 사용자 몇 명이 실제 청첩장을 만들어 보는 것까지.
- **2B (2주)** — 템플릿 3+2, 갤러리, 길찾기 링크, 미리보기 다듬기, 만료 안내·연장, 조회수.
- **2C (3주, 프리미엄 기반 뒤)** — 발행권 결제, 프리미엄 템플릿, RSVP(참석 여부·인원·측 → 장부의 "사람"으로 미리 들어온다. docs/01 의 원래 구상), 유니버설 링크.

### 3.7 법·운영
- **이용약관이 필요하다.** 지금은 처리방침뿐이다. 공개 페이지에 올라가는 남의 이름·계좌는 발행자 책임이라는 점, 신고·삭제 요청 창구, 만료 뒤 삭제 규칙을 적는다.
- 처리방침 갱신 — 사진, 공개 페이지, 조회수, 보관 기간.
- 부고장은 고인·상주의 정보라 민감하다. 표준 관행(상조 문자)과 같은 수준으로만 보여 주고, 발행자가 언제든 내릴 수 있게 한다.

## 4. 기능 ③ 문자 발송

### 4.1 먼저 알아 두실 사실 (조사 결과)

1. **앱이 문자를 대신 보낼 수 없다.** iOS 는 시스템 문자 작성 창을 띄워 사용자가 "보내기"를 눌러야만 간다. 안드로이드는 `SEND_SMS` 권한을 **기본 문자 앱으로 등록된 앱에만** 허용한다. 우리 앱은 해당하지 않으므로 선언조차 할 수 없다. [Google Play 정책](https://support.google.com/googleplay/android-developer/answer/10208820)
2. **iOS 작성 창에 수신자를 여러 명 넣으면 단체 대화방이 된다.** 받는 사람끼리 서로 번호가 보인다. 청첩장·부고에는 쓸 수 없으므로 한 명씩 띄워야 한다.
3. **서버에서 보내려면 발신번호를 사전 등록해야 한다.** 전기통신사업법 제84조의2. 번호 명의자 확인 서류(통신서비스 이용증명원 등)가 필요하다. [제도 안내](https://www.smsko.co.kr/info_law/law_callback.html) **그래서 사용자 각자의 번호로는 보낼 수 없다.** 신랑·신부마다 통신사 서류를 내게 할 수는 없다. 우리 서비스 번호로 보내고 본문에 "신랑 ○○○ · 신부 ○○○" 와 회신 연락처를 적는다. 기존 모바일 청첩장 업체들이 이렇게 한다.
4. **원가** — 솔라피 기준 SMS 18원, LMS 45원(VAT 별도). 링크를 넣으면 90바이트를 넘겨 LMS 가 된다. 100명이면 약 4,500원. [솔라피 가격](https://solapi.com/pricing)
5. **연락처 접근은 애플이 까다롭게 본다.** 전체 주소록을 올리면 안 되고, 사용자가 고른 사람만 써야 한다. [App Review Guidelines 5.1.1](https://developer.apple.com/app-store/review/guidelines/)

이 사실들 때문에 "전화번호부에서 골라서 앱이 쭉 보낸다"는 그림은 **무료 단계에서는 반쯤만, 유료 단계에서는 서버 발송으로** 가능하다.

### 4.2 이 앱만의 가치 — 수신자가 "사람"이 된다
문자를 보낸 사람 명단은 곧 **하객 후보 명단**이다. 보낼 때 선택한 사람을 장부의 `people`(이름·전화 — `phone` 열이 이미 있다)로 넣어 두면, 식이 끝나고 명부를 입력할 때 자동완성에 바로 뜨고, 나중에 "초대했는데 안 온 사람"도 가려낼 수 있다. 다른 문자 발송 앱에는 없는 연결이다.

### 4.3 단계

**3A — 연락처 선택 + 한 명씩 보내기 (2주, 무료, 서버 없음)**
- `expo-contacts` 로 연락처 권한을 받는다(iOS 18 의 "일부만 허용"도 받아들인다). 앱 안에서 검색·다중 선택. **주소록은 서버로 올리지 않는다.** 장부의 사람 목록에서도 고를 수 있다.
- 메시지 틀 — `{이름}` 치환, 청첩장 링크 자동 삽입, 종류별 기본 문안(청첩·부고).
- 보내기 — 수신자마다 시스템 문자 창을 띄우고, 보낸 사람에 체크가 쌓이는 진행 목록. 30명이면 30번 누른다. **이 한계를 화면에 솔직히 적는다.** 사용자 본인 번호로 가고 비용이 0원이라는 장점이 있다.
- 선택한 사람을 장부의 사람으로 넣을지 묻는다.

**3B — 서버 발송 (2주 + 서류 1~2주 병행, 유료)**
- 엣지 함수 `send-messages` — 로그인·장부 확인, 크레딧 차감, 1회 최대 수신자 수와 시간당 한도, 솔라피 호출, 발송 기록.
- 발송 기록은 **번호를 마스킹해서** 남긴다(010-****-1234, 건수, 시각, 결과). 원문 번호는 발송 직후 지운다.
- 발신번호 — 서비스 번호 하나를 등록한다. 사장님 명의 휴대폰이나 070 번호. 개인사업자로 솔라피에 가입한다(§6 결정).
- 본문 규칙 — 발신자 이름과 회신 번호를 항상 넣는다. 광고가 아니므로 수신거부 문구 의무는 없지만, 부고가 아니면 21시~08시 발송을 막는다.
- 가격 — 100건 9,900원 같은 묶음(소모성 인앱 결제). 원가 4,500원, 애플 수수료 15% 를 빼면 남는다. 인앱 결제로 파는 이유는 애플 심사의 회색 지대를 피하기 위해서다.

### 4.4 법·운영
- 처리방침 — "연락처(사용자가 고른 항목만)", 발송 기록 보관 기간. App Privacy 에 연락처 추가.
- 수신자 번호는 처리 위탁(솔라피)이 생기므로 처리방침의 위탁 표에 추가한다.
- 카카오톡 친구에게 보내기는 하지 않는다. 카카오 로그인·친구 동의·비즈 앱 심사가 따라온다. 카카오톡 공유는 ②의 공유 시트로 충분하다.

## 5. 공통 — 프리미엄 기반 (3주, ② 2B 뒤)

- `entitlements` (user_id, product, quantity, expires_at) 와 `credits` 원장. 발행권·문자 묶음은 소모성이라 잔량을 서버가 센다.

- 상품 — 청첩장 발행권(9,900원), 문자 100건(9,900원). 가격은 가설이다.
- **사장님이 하실 것** — App Store Connect 유료 앱 계약, 은행·세금 정보(개인사업자 등록증 기준). 며칠 걸린다. Apple 소규모 사업자 프로그램(수수료 15%)도 신청한다.
- 안드로이드 출시 전까지는 iOS 결제만 켠다.

## 8. 위험

- **카카오톡 미리보기 캐시** — 청첩장을 고친 뒤에도 옛 미리보기가 남는다. 발행 화면에 "카카오 캐시 초기화" 안내를 넣는다(랜딩에서 이미 겪은 일).
- **부고의 시간 압박** — 입력이 길면 쓰지 않는다. 2A 에서 실제로 10분 안에 끝나는지 재 본다.
- **문자의 기대 차이** — "앱이 알아서 보내 주겠지"라고 기대한다. 3A 화면에서 한 명씩 눌러야 한다는 것을 숨기지 않는다. 숨기면 별점이 떨어진다.
- **애플 심사** — 연락처·사진·인앱 결제가 한 번에 늘어난다. 심사 메모를 미리 쓰고, 연락처는 "선택한 사람만" 이라는 점을 화면과 메모에 명시한다.
- **공개 페이지 남용** — 추측 불가 slug, 조회수 외 추적 없음, 신고 창구. 약관 없이 공개 페이지를 열지 않는다.

## 📋 CTO 보고 요약

- 세 기능은 서로 얽혀 있다. **도메인 → 청첩장 → 문자 → 유료** 순이 맞다. 청첩장 공개 페이지의 카카오톡 미리보기가 서버 처리를 요구해서 도메인·호스팅 이전이 전제가 된다.
- 청첩장은 템플릿을 HTML 한 벌로 만들어 앱 미리보기와 공개 페이지가 같은 코드를 쓴다. 공개 읽기는 RPC 하나로만 열고 만료·삭제를 서버가 집행한다.
- 문자는 플랫폼과 법이 "앱이 대신 보내기"를 막는다. 무료 단계는 한 명씩 시스템 창, 유료 단계는 서비스 번호로 서버 발송이다. 사용자 번호로는 보낼 수 없다.
- 유료는 구독보다 1회 구매가 맞고, 인앱 결제로 간다. 사업자등록이 있으면 결제·세금·발신번호가 전부 쉬워진다.
- 전체 약 3개월. 1주차는 비용 3만원으로 끝난다.
