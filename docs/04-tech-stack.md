# 뿌린대로거두리라 — 기술 스택 후보 비교와 CTO 추천안

> 작성일 2026-09-14 · 작성 cto-orchestrator · 상태 **추천안(사용자 최종 결정 대기)**
> 판단 근거는 2026-09-14 로컬 실측 결과(context-notes.md "기술 환경 발견")에 기반한다.

## 0. 판단의 전제

- 1인 개발이며, iOS와 Android를 모두 출시한다(가정. 한쪽만 먼저 낼 수도 있으므로 사용자 확인 질문에 포함).
- 1단계는 개인 장부이고 2단계는 공개 웹 페이지(청첩장)와 계정이 필요하다. 따라서 스택은 1단계의 단순함과 2단계의 웹 확장을 동시에 만족해야 한다.
- 실측된 환경 — Xcode 26.6, Android Studio + SDK, Node 26, Bun, CocoaPods 있음. Flutter/Dart 없음. 사용자 실전 경험은 Swift(321go 출시), Kotlin/Compose(321go 베타), Expo(FluencC SDK 57, scentilique), Next.js + Supabase(coco-finance).

**CTO 추천 — A. React Native + Expo(TypeScript).** 근거는 세 가지다.
1. 이미 두 프로젝트에서 검증한 스택이라 착수 비용이 가장 낮고, 로컬 툴체인이 전부 준비돼 있다.
2. 2단계 청첩장은 결국 웹 페이지다. TypeScript 도메인 타입(행사·사람·기록)을 앱과 웹이 그대로 공유하는 경로는 A뿐이다.
3. 321go에서 네이티브 두 벌을 유지하며 Android가 뒤처진 경험이 있다. 1인 개발에서 C는 감당하기 어렵다.

대안으로 **C(네이티브)** 를 고를 만한 경우는 "iOS만 먼저 출시하고 Android는 미정"일 때다. 그 경우에도 2단계 웹 공유를 생각하면 A가 여전히 우세하다.

## 2. 백엔드·DB — 로컬 우선 대 클라우드 동기화

| 기준 | 1. 로컬 우선(SQLite) | 2. 클라우드 우선(Supabase) | 3. 로컬 SoT + 나중에 동기화 추가 |
|---|---|---|---|
| 온보딩 | 설치 즉시 사용, 로그인 없음 | 회원가입·로그인 필수 | 1과 동일 |
| 프라이버시 | 서버에 데이터 없음. 개인정보 처리 부담 최소 | 서버 보관에 따른 처리방침·보안 책임 | 동기화 켜기 전까지 1과 동일 |
| 기기 변경·분실 | OS 백업 + 내보내기로 대응. 완전 자동은 아님 | 자동 | 동기화 후 자동 |
| 구현 난이도 | 가장 낮음 | 낮음(사용자가 익숙) | 동기화 엔진(충돌 해결)이 어려움 |
| 2단계 적합성 | 청첩장은 별도 서버 필요 | 그대로 확장 | 서버 도입 시점에 마이그레이션 필요 |
| 오프라인 | 완전 | 캐시 필요 | 완전 |

**CTO 추천 — 1단계는 로컬 우선(SQLite), 단 스키마는 처음부터 클라우드 이전이 가능하게 설계한다.**
- 장부 데이터는 민감하고 개인적이다. 로그인 없이 바로 쓰는 경험이 1차 세그먼트(식장 가는 길에 30초 기록)에 결정적이다.
- 2단계에서 계정을 도입할 때 "로컬 데이터를 서버로 1회 업로드하고 이후 서버를 SoT로 전환"하는 단순한 경로를 택한다. 양방향 동기화 엔진은 만들지 않는다. 이를 위해 1단계 스키마는 모든 행에 **UUID 기본키, `created_at`/`updated_at`, 소프트 삭제(`deleted_at`)** 를 둔다.
- 반대 선택(클라우드 우선)이 나은 조건은 "출시 초기부터 부부 공동 관리가 필수"일 때다. 이 조건은 사용자 확인 질문에 포함했다.

### 저장 계층 세부
- **expo-sqlite** + **Drizzle ORM**(expo-sqlite 드라이버, `drizzle-kit`으로 마이그레이션 생성). 타입 안전한 스키마와 마이그레이션 이력이 생기고, 2단계 Postgres 전환 시 도메인 타입은 재사용된다(단 SQLite용 `sqliteTable` 선언은 `pgTable`로 다시 써야 한다. 스키마 파일 자체가 자동 이식되진 않는다).
- DB 파일 위치는 expo-sqlite 기본 경로(앱 Documents 하위 `SQLite/`)를 그대로 쓴다. iOS는 Documents가 iCloud 백업에 기본 포함되고, Android는 자동 백업(앱당 25MB 한도)이 DB 디렉터리를 포함한다. 장부 데이터는 텍스트라 수만 건이어도 25MB에 한참 못 미친다.
- 그 위에 **JSON 내보내기/가져오기**(공유 시트로 파일 저장)를 1단계에 넣는다. OS 백업이 실패하는 경우(다른 OS로 기기 변경)를 위한 최후 수단이다.

## 3. 인증

- 1단계 — **없음.** 로컬 앱이므로 계정이 필요 없다. 선택 기능으로 **앱 잠금(생체 인증, expo-local-authentication)** 을 두면 민감 데이터 우려를 낮출 수 있다. MVP 포함 여부는 사용자 확인 질문에 넣었다.
- 2단계 — Supabase Auth. 한국 사용자 기준 Apple·Google 로그인은 필수(스토어 정책상 Apple 로그인은 소셜 로그인을 넣는 순간 의무), Kakao 로그인은 OIDC 커스텀 프로바이더로 추가 가능. 사용자가 scentilique에서 이미 Supabase Auth를 다뤘다.

## 4. 앱 구조와 라이브러리 (1단계)

| 영역 | 선택 | 이유 |
|---|---|---|
| 언어·런타임 | TypeScript, Expo SDK 57 이상(FluencC에서 검증된 버전 계열) | 실측된 기존 프로젝트와 동일 |
| 패키지 매니저 | npm | pnpm·yarn 없음. 기존 Expo 프로젝트와 통일 |
| 라우팅 | Expo Router | 파일 기반, 딥링크 기본 지원(2단계 청첩장 링크에서 앱 열기 대비) |
| 상태·데이터 | 리포지토리 함수(SQL) + TanStack Query, 키 규칙 `[domain, action, params]` | 사용자의 기존 규칙과 동일. 전역 상태 라이브러리는 필요 전까지 도입하지 않음 |
| UI | React Native 기본 컴포넌트 + StyleSheet + 디자인 토큰 파일 1개 | 추가 UI 프레임워크 없이 시작. 필요해지면 NativeWind 검토 |
| 도메인 로직 | `src/domain/`에 순수 함수(금액 합산, 사람별 수지, 이름 정규화)로 분리 | `node --test`로 빌드 없이 단위 테스트(Node 26 타입 스트리핑, scentilique 전례) |
| 연락처 | expo-contacts, 권한은 선택 | 권한 거부 시에도 수동 입력으로 동작해야 함 |
| 알림 | expo-notifications 로컬 알림만 | 서버 푸시 불필요 |
| 파일 | expo-file-system + expo-sharing | 내보내기/가져오기 |

리포지토리는 **단일 앱**으로 시작한다. 2단계에서 웹(Next.js)이 추가될 때 scentilique처럼 npm workspaces 모노레포(`apps/mobile`, `apps/web`, `packages/domain`)로 재편한다. 지금 모노레포를 만드는 것은 과설계다.

| 개인정보 처리방침 | 로컬 저장이어도 스토어 등록에 필수 | 연락처 권한을 쓰면 수집 항목에 명시 |

## 6. 명시적으로 하지 않는 것 (1단계)

- 서버·API·회원가입. 2단계에서 도입한다.
- 양방향 동기화 엔진. 2단계 전환은 1회 업로드 방식으로 간다.
- 모노레포, 디자인 시스템 패키지, 전역 상태 라이브러리. 필요가 증명되기 전까지 만들지 않는다.
- Flutter·KMP 재검토. 사용자가 명시적으로 원하지 않는 한 A로 확정한다.

## 7. 사용자 결정이 필요한 항목 (요약)

1. 프레임워크 — 추천 A(Expo). 대안 C(네이티브 iOS 우선).
2. 저장 방식 — 추천 로컬 우선. 대안 클라우드 우선(부부 공동 관리가 초기 필수일 때).
3. 출시 플랫폼 — iOS·Android 동시인지, iOS 우선인지.
4. 앱 잠금(생체 인증) MVP 포함 여부.
